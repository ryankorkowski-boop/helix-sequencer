# Issue #41 — BeatGrid Alignment Implementation Status

## Goal

Every timing event generated by Helix should be able to align deterministically to a musical grid derived from BPM, subdivision, and optional offset. The implementation preserves raw timing while exposing snapped timing for export, scoring, debugging, and future learning.

## Implemented modules

### Core grid engine

- `core/beat_grid.py`
  - `BeatGrid`
  - `generate_beat_grid`
  - `snap_to_grid`
  - threshold-aware snapping
  - strict / musical / humanized modes
  - ordering preservation

### Timeline integration

- `core/timeline_beat_grid.py`
  - lyric line snapping
  - word snapping
  - phoneme snapping
  - `build_lyric_timeline_with_grid`
  - `snap_song_parts_to_grid`
  - `snap_part_hits_to_grid`

### Runtime and Prime policy

- `core/beat_grid_runtime.py`
  - parses `--snap-grid`, `--snap-bpm`, `--snap-offset-ms`, `--snap-mode`, `--snap-max-shift-ms`, `--no-snap`

- `core/beat_grid_bpm.py`
  - extracts BPM from report payloads
  - median fallback across report estimates
  - fallback to 120 BPM only when no better source exists

- `core/prime_beat_grid.py`
  - Prime/master default activation policy
  - default 16th-note musical grid
  - explicit runtime flags override defaults
  - `--no-snap` disables snapping

### Scoring

- `core/self_improving_scoring.py`
  - added `rhythmic_accuracy`
  - scores raw-vs-snapped timing deltas
  - contributes to composite self-improving score

### Snowman Band / drummer

- `core/snowman_band_beat_grid.py`
  - payload-wide snapping for band plans
  - lyric, phoneme, part, hit, face, performer, and timing payloads

- `core/drummer_beat_grid.py`
  - classifies kick/snare/hat/fill/crash-like events
  - cymbal crashes prefer strong beats
  - fills prefer finer subdivisions
  - kick/snare stay on groove grid

### xLights / XSQ integration

- `xlights/beat_grid_timing.py`
  - snaps xLights timing-track events inside XSQ XML
  - preserves `rawStartTime` / `rawEndTime`
  - writes `snappedStartTime` / `snappedEndTime`
  - protects `HX*` tracks by default

- `core/beat_grid_output_postprocess.py`
  - postprocesses reports, Snowman Band JSON, and XSQ timing tracks

### Wrappers / validation

- `core/sequence_builder_beat_grid.py`
  - BeatGrid-aware CLI wrapper

- `core/effect_engine_beat_grid.py`
  - BeatGrid-aware effect-engine wrapper

- `tools/beat_grid_validation.py`
  - before/after validation harness for generated output folders

## Validation command

Run after generating outputs:

```bash
python tools/beat_grid_validation.py <output-folder> --subdivision 16 --mode musical --out beat_grid_validation.json
```

Recommended targets:

```bash
python tools/beat_grid_validation.py aaatest --out validation_aaatest.json
python tools/beat_grid_validation.py helixia --out validation_helixia.json
python tools/beat_grid_validation.py snowman_band --out validation_snowman_band.json
```

## Remaining integration work

The feature infrastructure is implemented. Remaining work is mainly direct production-path wiring and real-world validation:

1. Run the new tests in CI.
2. Wire `prime_beat_grid_args` or `decide_prime_beat_grid` into the canonical `sequence_builder` / `effect_engine` path once the large-file patch can be applied safely.
3. Run `tools/beat_grid_validation.py` against actual generated outputs.
4. Inspect xLights render previews for timing feel.
5. Tune thresholds if validation shows over-snapping:
   - vocals: likely 25–40 ms
   - kick/snare: 40–55 ms
   - crashes: 60–80 ms
   - fills: 40–60 ms

## Notes

This implementation intentionally preserves raw timing everywhere possible. Existing downstream emitters can continue reading normal timing fields, while scoring/debugging can compare raw and snapped values.

The largest remaining risk is not the BeatGrid math; it is production-path integration with the existing large `core/effect_engine.py` file. Use small, surgical patches and validate after each one.
